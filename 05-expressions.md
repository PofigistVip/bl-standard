# 5. Выражения и операции

Источники: `C/grammar/Grammar.y`; `C/java/org/zenframework/z8/compiler/parser/expressions/`; `parser/type/members/{Operator,PriorityOperator,CastOperator}.java`; `L/org/zenframework/z8/lang/*.bl`.

## 5.1 Приоритет и группировка

Таблица следует иерархии продукций `Grammar.y`, от более сильной к более слабой. Точное разрешение неоднозначностей определяется yacc-грамматикой и сгенерированным parser; не все операции являются свободно цепляемыми.

| Уровень | Форма | Группировка по продукции |
|---|---|---|
| первичные/постфиксные | литерал, имя, `this`, `super`, `container`, скобки, вызов, `.`, `[]`, `new`, приведение | постфиксные формы могут продолжаться |
| унарные | `+ - ! ~` | рекурсивно справа |
| мультипликативные | `* / %` | слева |
| аддитивные | `+ -` | слева |
| отношения | `< > <= >=` | только одна операция на уровне без дополнительных скобок |
| равенство | `== !=` | только одна операция на уровне без дополнительных скобок |
| побитовое И, XOR, ИЛИ | `&`, `^`, `\|` | каждый уровень слева |
| логическое И, ИЛИ | `&&`, `\|\|` | каждый уровень слева |
| условное | `condition ? a : b`, `a ?: b` | см. продукцию `ternaryExpression` |
| проверка типа | `expression instanceof простойТип` | внешняя продукция expression |
| присваивание | `= += -= *= /= %= &= \|= ^=` | отдельная продукция `assignment`, не обычный уровень `expression` |

Запись `a = b = c` нельзя считать допустимой только по аналогии с Java: правая часть присваивания задаётся `expression`, а не `assignment`. Унарный `+` в грамматике не вызывает `parser.onUnary`; это отличается от `-`, `!`, `~` и требует осторожности при выводах о вызове перегруженного оператора.

## 5.2 Разрешение операций и вызовы

Методы и операторы перегружаются: компилятор разрешает типы получателя и аргументов, проверяет доступность, статический контекст и применимые преобразования; отсутствие кандидата и неоднозначность диагностируются. Реальное действие численных и других операций задаётся объявленным оператором типа и его Java-реализацией. Например, `int.bl` объявляет арифметику с `int` и `decimal`, а `bool.bl` — `!`, `&&`, `||`, `==`, `!=`. Нельзя без отдельной проверки приписывать всем типам одни и те же операторы или универсальное переполнение.

Компилятор отдельно генерирует для `bool && bool` и `bool || bool` условный Java-код с коротким замыканием: правый операнд вычисляется только при необходимости. Для других применимых перегрузок правила вычисления выводятся из `BinaryExpression.getCode` и реализации оператора; не следует автоматически обобщать короткое замыкание.

`this` и `super` обозначают текущий контекст объекта и контекст базового типа; их допустимость определяется семантическим анализом. `container` и повторное `container.container` переходят по содержащим типам, запрещены при отсутствии нужного контейнера и в статическом контексте. Доступ — через `.`; вызов имеет вид `имя(аргументы)` или `получатель.имя(аргументы)`. Аргументы могут включать литеральные инициализаторы коллекции с ожидаемым типом.

### 5.2.1 Выбор перегрузки метода

1. `MethodCall` получает кандидаты с заданным именем из типа получателя и его базовых типов; `AbstractType.getMatchingMethods` удаляет повторяющиеся сигнатуры, начиная с более производного типа.
2. Для каждого метода проверяются число аргументов и возможность преобразовать каждый аргумент к типу соответствующего параметра. Неприменимые кандидаты отбрасываются.
3. Каждый подходящий набор преобразований получает сумму весов: пользовательское преобразование добавляет 100, остальные преобразования — 0. Выбирается наименьший вес; при равенстве лучших весов компилятор сообщает о неоднозначности. Расстояние наследования в этом сравнении не учитывается, как показано в [разделе 4](04-types.md).
4. После выбора проверяются статический контекст и видимость метода. Вызов статического метода через экземпляр может сопровождаться предупреждением.

Поскольку специальный тип `null` предоставляет преобразование к кандидатному типу, `pick(null)` при перегрузках `pick(int)` и `pick(string)` в проверенном примере неоднозначен. Это не утверждение о допустимости всех вызовов с `null`; см. `MethodCall.checkSemantics`, `TypeCastSet` и тест `null makes overload ambiguous`.

### 5.2.2 Наблюдаемый алгоритм бинарного оператора

`BinaryExpression.checkSemantics` сначала рассматривает операторы с одним параметром у левого типа и совместимое преобразование правого аргумента. При одном лучшем кандидате он используется; несколько одинаково подходящих приводят к диагностике. Если прямого кандидата нет, компилятор рассматривает операторы преобразования левого типа и ищет операцию у результатов этих преобразований. Ноль вариантов — неопределённая операция, больше одного — неоднозначность. Это асимметричный поиск: нельзя предполагать автоматическую перестановку операндов.

Если любой операнд имеет специальный тип `null`, проверка в `BinaryExpression` возвращает успех до обычного поиска операции, а генерация вставляет знак между Java `null` и другим операндом и оборачивает результат в `bool`. Это особенность backend: принятие компилятором само по себе не гарантирует, что любой такой знак образует допустимую Java-операцию или что вызов безопасен. Например, `null && true` принимается BL-компилятором, но сгенерированный Java-код отвергается `javac` из-за типов операндов. Для enum генератор также имеет отдельную ветвь сравнения. Правила перегрузки отдельных унарных операций реализованы в `UnaryExpression`.

### 5.2.3 Скобки и priority-оператор

Скобки могут иметь семантический эффект: `BracedExpression.getCode` при единственном доступном `operatorPriority` генерирует вызов `operatorPriority()` для заключённого выражения; для ссылочного типа перед вызовом вставляется `.get()`. Для тернарного выражения имеется отдельная ветвь генерации скобок. В SQL-типах priority-оператор строит узел `Group`, а не просто изменяет текст исходника. См. также [SQL-выражения](13-sql-expressions.md).

Дополнительно `JumpStatement.getCode` после возвращаемого выражения вызывает priority-оператор, если возвращаемый тип метода имеет ровно один такой оператор. Это относится и к `return` без скобок. Для проверенного ссылочного пользовательского типа, чей `operator()` содержит `return this;`, BL-компилятор принимает программу, но `javac` отвергает вызов `operatorPriority()` у `CLASS`-обёртки. Тест: `priority operator reference return`; это особенность backend, не гарантия работоспособности каждой декларации `operator()`.

## 5.3 Создание, проверка типа и выбор

Грамматическая форма создания — `new Identifier`, без обязательных скобок и аргументов. `OperatorNew` разрешает этот тип и генерирует создание через `VariableType.getJavaNew`; наличие Java-конструктора с аргументами нельзя предполагать по аналогии с Java.

Для `условие ? a : b` условие приводится к `bool`. Компилятор сначала пытается преобразовать тип `a` в тип `b`; при успехе выбирается тип `b`, иначе пытается преобразовать `b` в `a`. Если оба направления недоступны, выдаётся ошибка. На этапе исполнения вычисляется выбранная ветвь.

`a ?: b` возвращает `a`, если результат `a` не равен `null`, иначе вычисляет и возвращает `b`; `a` вычисляется один раз во временную переменную. Результат имеет тип `a`; `b` должен приводиться к нему. Речь о проверке null, не о проверке пустой строки, нуля или `false`.

`x instanceof T` задаётся с простым типом, не массивной продукцией `type`. Доступность и результат зависят от проверок `InstanceOf.java` и представления объектов runtime.

## 5.4 Присваивание

Левая часть должна представлять переменную/допустимое левое значение. Присваивание проверяет совместимость и может использовать `operator =`; составные присваивания переводятся через соответствующий оператор и присваивание. В теле класса `qualifiedNameInit` отдельно поддерживает простую форму, `=` и `+=`. При составном присваивании `Parser.onOperatorAssign` помещает тот же левый элемент и в бинарное выражение справа; сгенерированный код может вычислить сложный левый операнд дважды. В выполненном тесте `fetch().field += 1` метод `fetch()` вызван дважды, тогда как в `fetch().field = 1` — один раз. См. `Initialization.getCode` и тесты `compound receiver evaluated twice`, `simple receiver evaluated once`.

## 5.5 Порядок вычислений в проверенном backend

Для проверенных вызовов аргументы вычисляются слева направо; аналогичный порядок наблюдается у двух операндов обычного `+`. Для `bool &&` и `bool ||`, а также `?:` проверено отсутствие вызова невыбранной правой части. Для остальных конструкций следует учитывать фактический сгенерированный Java-код и вызываемые операторы.

В инициализаторе карты кодогенератор сначала формирует Java-массив всех ключей, затем отдельный Java-массив всех значений. Поэтому для двух пар `(mark(1), mark(2)), (mark(3), mark(4))` в тесте порядок побочных эффектов — `1, 3, 2, 4`, а не порядок пар в тексте. Для обычного списка генератор формирует один массив элементов. Источник: `ArrayInitializer.getCode`; тест `map initializer order`.

При проверенных `int[] a` и `int[int] m` формы `a[0] = 9`, `a[0] += 4` и `m[1] = 5` проходят BL-компилятор, но созданный Java-код содержит недопустимую левую часть и отвергается `javac` с `unexpected type`. Это ограничение конкретной генерации, а не вывод о каждой возможной перегрузке присваивания индексированного значения. Для изменения проверенного массива работает объявленный метод `set`; для карты — `add(key, value)`. См. `ArrayAccess.getCode`, `Initialization.getLeftSideCode` и соответствующие проверки `array indexed assignment`, `array compound assignment`, `map indexed assignment`.
